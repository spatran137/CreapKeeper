# CreapKeeper v1.3.0 — Checking for Updates

For a project I have been using to test different ideas, I thought another interesting one would be having the application recognize that I published a new GitHub release.

I did not want to set up an update server or require people to sign in to GitHub. Since this repository is public, it turns out GitHub Releases can provide the information the app needs.

## What's new

- **Check for updates** in the app window and Windows system tray.
- An optional startup check for stable releases, limited to once every 24 hours.
- A prompt when GitHub has a newer version, with a choice to install or leave it for later.
- Download of the portable \`CreapKeeper.exe\` release asset using HTTPS.
- Verification of the advertised file size and SHA-256 digest from GitHub Releases before installation.
- A temporary helper that waits for the application to exit, backs up the previous executable as \`CreapKeeper.exe.previous\`, replaces it, and restarts CreapKeeper.

## Getting started

This part is important: **v1.2.0 does not have an updater**. To get this feature you first need to download **v1.3.0 manually**. After that, CreapKeeper can check future releases itself.

By default, packaged Windows builds check GitHub once a day when launched. You can turn this off in the Updates section or use **Check for updates** manually. No new executable is installed unless you agree.

Updates need outbound internet access to GitHub, but **The Creap Report** still works entirely on your LAN. No counts, history, or database contents are sent to GitHub.

## Things to know

The portable executable needs to be in a folder your Windows account can write to for replacement to work. A protected location like \`C:\Program Files\` may require a manual update instead. Python source checkouts will open the release page rather than overwrite themselves.

The SHA-256 check verifies the download against GitHub's release metadata; the app is still unsigned. The existing SQLite database, old Count and **Creap** identifiers, LAN settings, and firewall configuration are not changed.

Automated tests cover version parsing, release metadata, bad downloads, preferences and install restrictions. The actual close-replace-restart sequence still needs manual testing with the packaged Windows executable before I can call that fully validated.

## Final thoughts

This has become a surprisingly useful little project for learning how real desktop apps work. There is now an updater for an application whose original purpose was counting someone appearing behind a chair. I am sure the 2017 version did not see that coming.
